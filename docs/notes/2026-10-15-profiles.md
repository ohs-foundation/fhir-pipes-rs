# Profiles: moving ICR's mappings out of the code

Design note for review before implementation. 2026-10-15.

## The problem

The Location commands (`transform locations`, `diff`, `index`, `dhis2`,
`population`) were written for the Integrated Campaign Registry (ICR) and
have its implementation guide (IG) built in. About 350 lines across 22 files
name ICR URLs, codes or columns:

- **Extension URLs and code systems** under `https://icr.healthcampaigns.org`:
  settlement type, delivery strategy, ownership, facility type, overlays,
  spatial index, the boundary attachment, and the population Group profile
  and its extensions.
- **Identifier systems:** pcode (falling back to `national-admin-code`),
  Overture GERS, and Nigeria's NHFR code and UID.
- **Location columns:** `pcode`, `gers_id`, `settlement_type`,
  `delivery_strategy`, `facility_level`, `ownership`, `nhfr_code`,
  `nhfr_uid`, `facility_level_text` and `ownership_text`. Each is a named
  field on `Location` or `Organization`, a column in `write/schema.rs`, and a
  branch in the `match` in `diff/rebuild.rs` that writes it back.
- **Type codes:** `admin-unit`, `facility`, `settlement`, `*-catchment`, used
  by the hierarchy, DHIS2 import and the tiles step.
- **DHIS2 import:** the ICR Location and facility Organization profiles,
  the location-type system, and the project tag system.

fhir-data-pipes can't take a tool where another deployment has to change
the code to use its own IG.

## What stays built in

Everything that comes from base FHIR R4 rather than an IG:

- id, name, status, `partOf` and the hierarchy derived from it
- `position`, `physicalType`, `managingOrganization` and the Organization
  pairing through it
- `identifier` as a list, `fhir_json` and `organization_json`
- geometry from `position` and from the HL7 `location-boundary-geojson`
  extension
- the report, partitioning, GeoParquet writing, and `diff`/`load`'s version
  checks

## What moves to a profile

A profile is a TOML file. It names the IG-specific URLs and codes, and
declares the extra columns. Each column says where its value lives in a
resource, in a form `diff` can follow back to write an edit.

```toml
# profiles/icr.toml
name = "icr"
base = "https://icr.healthcampaigns.org"

[location]
boundary_extensions = ["https://icr.healthcampaigns.org/StructureDefinition/location-boundary-geojson"]
overlays_extension = "https://icr.healthcampaigns.org/StructureDefinition/location-overlays"
type_system = "https://icr.healthcampaigns.org/CodeSystem/icr-location-type-cs"
admin_unit_type = "admin-unit"

# Extra columns, in output order. Kinds:
#   extension_code  extension[url].valueCode
#   identifier      the first identifier under one of `systems` (diff writes the first)
#   type_coding     the code under `system` in `type` (a CodeableConcept list)
#   type_text       the text of the `type` concept holding a coding under `system`
[[location.column]]
name = "pcode"
kind = "identifier"
systems = ["https://icr.healthcampaigns.org/identifiers/pcode",
           "https://icr.healthcampaigns.org/identifiers/national-admin-code"]

[[location.column]]
name = "settlement_type"
kind = "extension_code"
url = "https://icr.healthcampaigns.org/StructureDefinition/settlement-type"

# … gers_id, delivery_strategy, facility_level, ownership

# Columns read from the Organization paired through managingOrganization.
# A Location column with the same name wins, as today.
[[organization.column]]
name = "nhfr_code"
kind = "identifier"
systems = ["https://icr.healthcampaigns.org/identifiers/nga-nhfr-code"]

[[organization.column]]
name = "facility_level_text"
kind = "type_text"
system = "https://icr.healthcampaigns.org/CodeSystem/icr-facility-type-cs"

[dhis2]
location_profile = "…"
facility_organization_profile = "…"
project_tag_system = "…"

[population]
group_profile = "…"
# the extension URLs and source-code system it writes
```

**In the code:**

- `Location` and `Organization` keep the base fields and gain
  `columns: Vec<Option<String>>`, filled in profile order.
- `write/schema.rs` builds the column list from the profile.
- `diff/rebuild.rs` replaces its named branches with one function per column
  kind, which writes the edit back.
- The tiles step reads its type codes and `*_text` columns from the profile.

## Choosing the profile

- `--profile NAME|FILE` on the Location and DHIS2 commands.
- `profile = "…"` in `fhir-pipes.toml` for `refresh`.
- `snapshot/state.json` records the profile a snapshot was transformed
  with, so a later `diff` uses the same one without being told.
- Built-in profiles are embedded in the binary:
  - `base`: no extra columns
  - `icr`: today's behaviour, column for column

## Decisions needed

1. **The default profile.**
   - *Recommended:* `base` as the default, with ICR choosing `icr` explicitly
     in its `fhir-pipes.toml` and scripts. That's cleaner for fhir-data-pipes,
     but anyone running the Location commands by hand for ICR must add
     `--profile icr`.
   - *Alternative:* keep `icr` as the default for now, which changes nothing
     for anyone, and switch the default when the tool moves into
     fhir-data-pipes.
2. **Where `icr.toml` lives.**
   - *Recommended:* in fhir-pipes (`profiles/icr.toml`, embedded), as the
     worked example.
   - *Alternative:* in the ICR repo, read as a file.
3. **Scope of the first change.**
   - *Recommended:* Location and Organization columns, URLs and type codes
     first, since those decide the Parquet schema and `diff`.
   - *Then:* the DHIS2 and population constants, which are only URLs.
4. **Column kinds.** The four above cover every ICR column today. A
   general FHIRPath for reading would be more flexible, but `diff` couldn't
   write it back. A view-only column could use FHIRPath if one is ever needed.

## Testing

- With `--profile icr`, the existing integration tests must pass unchanged.
  Those are transform, diff, index, dhis2, population and refresh, and they
  are the check that ICR's output hasn't moved.
- New tests: a `base` transform has only the built-in columns, a custom
  profile column round-trips through `diff`, and a profile with an unknown
  kind is refused.

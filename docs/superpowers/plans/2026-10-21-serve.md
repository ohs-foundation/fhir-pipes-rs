# fhir-pipes serve Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `refresh` stops cleanly on a signal and can report to a supervisor; `fhir-pipes serve` starts refreshes over HTTP or on a schedule, retries safe failures, and notifies configured destinations when a run ends.

**Architecture:** Two PRs. PR A changes `refresh` only: a process-wide stop flag (`src/stop.rs`) checked between steps, pages and resource types, held back during the commit window, plus a tool registry so a stop reaches running tools; `last-run.json` gains `committed`/`published`; two environment variables (`FHIR_PIPES_RESULT_FILE`, `FHIR_PIPES_FAILURE_HOOKS=off`) and `RUN_ID` for hooks. PR B adds `src/serve/`: an axum server on tokio, which runs each attempt as a child `fhir-pipes refresh` in its own process group, stores durable run records under `<data>/.serve/`, captures and redacts output, and sends notifies from a separate thread.

**Tech Stack:** Rust 2024, tokio (in tree), axum 0.8 (new), croner 2 (new, five-field cron), signal-hook 0.3 (new, PR A), libc (direct dependency; already in tree), reqwest blocking (in tree) for notify.

**Spec:** `docs/superpowers/specs/2026-10-21-serve-design.md`. Read it before any task; section names below refer to it.

## Global Constraints

- PR A branches from `refresh-run-outcome` (PR #136); PR B from PR A. One PR each, merged only after review feedback is in and addressed.
- Without `FHIR_PIPES_RESULT_FILE` and `FHIR_PIPES_FAILURE_HOOKS`, `refresh` behaves as PR #136 except for the new stop handling and the two new `last-run.json` fields.
- Signal handling and `serve` are `#[cfg(unix)]`. `serve` is not in the Windows binary; `refresh` on Windows keeps today's Ctrl-C behaviour.
- Exit codes: 0 success, 2 operator-fixable, 1 everything else. A stop is exit 1.
- Control records (`run.json`, result files) are written with `crate::fs::atomic_write` (fsync, rename, directory fsync).
- Defaults from the spec, verbatim: `--listen` `127.0.0.1:8090`; `retries = 2`; `retry_delay = 600`; `stop_grace = 120`; `keep_runs = 100`; `max_log_bytes = 20_000_000`; notify tries 3, waits 10 s then 60 s, connect timeout 10 s, overall 30 s, response read cap 64 KB; log line cut 64 KB; stdout queue 10,000 lines and 8 MB; `POST /run` body ≤ 16 KB; `?limit=` ≤ 500; `?tail=` ≤ 10,000; record-write retry every 30 s; tool stop SIGTERM then SIGKILL after 10 s; secrets shorter than 4 characters not replaced.
- Retryable `failed_step`s, verbatim: `lock`, `tools`, `start`, `files`, `locations`, `views`, `tiles`, `manifest`, `catalog`.
- Prose in docs and messages follows the repo's existing style: plain, literal, no headings that are slogans.
- `cargo clippy --all-targets --all-features -- -D warnings` clean and `cargo test` passing at every commit. Run tests with `env -u AI_AGENT -u CLAUDECODE` (duckdb's agent mode breaks the catalog tests otherwise).

## Review Focus

1. A `fhir-pipes.toml` with a `[serve]` section must still be accepted by `refresh`, whose config is `deny_unknown_fields` (Task B1 test `refresh_ignores_the_serve_section`).
2. `POST /run` with an empty body and no `Content-Type` (what an OpenFn `http.post` with no body sends) starts an incremental run, not a 400/415 (Task B6 test `an_empty_post_starts_an_incremental_run`).
3. A child that exits 0 without writing its result file is a success (Task B3 test `exit_0_without_a_result_file_is_success`).
4. `GET /runs/{id}/log?tail=50` on a 20 MB log reads from the end of the file, not the whole file (Task B4 test `tail_reads_only_the_end`).
5. `serve` started on a warehouse directory that does not exist yet creates it, `.serve/` included (Task B1 test `serve_creates_the_data_directory`).
